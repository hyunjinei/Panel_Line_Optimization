# RL 방법 선택 정당성

## 핵심 주장

PBS 스케줄링은 고정된 입력에 대해 한 번만 최적해를 찾는 문제가 아니다.  
작업 진행 상태, bay 점유 상태, 날짜별 용량, 생산 제약, 작업자 요청이 계속 바뀌는 순차 의사결정 문제다.

따라서 본 문제에는 정적인 규칙이나 매번 처음부터 다시 탐색하는 방식보다, 현재 상태를 보고 다음 블록을 선택하는 RL policy가 구조적으로 적합하다.

```text
현재 상태
-> 가능 후보 마스킹
-> 블록 하나 선택
-> bay/date/제약 상태 변경
-> 다음 상태에서 다시 선택
```

## 결과를 제외해도 RL이어야 하는 이유

### 1. 문제 자체가 순차 의사결정이다

앞에서 어떤 블록을 선택했는지에 따라 뒤의 가능 후보와 제약 위험이 달라진다.

예를 들어 다음 상태들이 매 step마다 바뀐다.

```text
남은 블록 목록
bay 사용 이력
날짜별 작업량
심수 누적량
P/S 연결 상태
C/Seam 간격 상태
작업장 순서 상태
```

이 구조는 RL의 상태, 행동, 보상 구조와 직접적으로 맞는다.

### 2. 현장 변화에 대응하기 쉽다

실제 현장에서는 아래 요청이 계속 들어올 수 있다.

```text
특정 블록 긴급 투입
자재 미입고
특정 날짜 작업 불가
특정 bay 사용 제한
일일 블록 수 제한
일일 심수 제한
앞쪽 시퀀스 고정 후 나머지만 재조정
```

휴리스틱은 이런 요청이 늘어날수록 규칙을 계속 새로 고쳐야 한다.  
GA는 요청이 바뀔 때마다 다시 탐색해야 한다.  
RL은 이미 학습된 policy가 바뀐 상태와 제약을 입력으로 받아 다시 decode할 수 있다.

### 3. LLM 연결과 역할 분리가 명확하다

LLM은 최적화기를 대체하지 않는다.  
LLM은 작업자의 자연어 요청을 구조화된 제약으로 바꾸는 입력 계층이다.

예시는 다음과 같다.

```text
"11번 블록은 세 번째로 해줘"
-> fixed_position

"11번은 4번보다 먼저 오게 해줘"
-> precedence

"11번 블록은 35A로 배정해줘"
-> manual_bay_assignment

"11일에는 15개까지만 해야 해"
-> date_specific_daily_block_cap

"C/Seam 간격은 runtime만 끄고 audit는 유지해줘"
-> constraint_toggle
```

이후 RL은 해당 제약이 반영된 상태에서 새 스케줄을 빠르게 생성한다.

정확한 표현은 다음과 같다.

```text
LLM은 사람의 요청을 제약으로 바꾸는 입력 계층이고,
RL은 그 제약이 반영된 동적 상태에서 빠르게 새 스케줄을 생성하는 의사결정 계층이다.
```

### 4. 마스킹과 policy를 함께 쓸 수 있다

RL은 제약을 무시하고 선택하는 방식이 아니다.

```text
불가능 후보: action masking으로 제거
가능 후보: RL policy가 우선순위 결정
최종 결과: final audit로 검증
```

즉, 현장 제약은 hard mask와 final audit가 담당하고, RL은 가능한 후보 중 장기적으로 나은 선택을 학습한다.

### 5. 반복 what-if 분석에 강하다

UI/LLM 기반 사용에서는 사용자가 계속 조건을 바꿀 수 있다.

```text
이 블록을 앞에 넣으면?
이 블록을 35A로 보내면?
이 날짜를 작업 불가로 만들면?
앞 5개는 고정하고 다시 짜면?
C/Seam runtime만 끄면?
```

이런 반복 요청에서는 매번 큰 탐색을 새로 수행하는 방식보다, 학습된 RL policy로 빠르게 재스케줄링하는 구조가 자연스럽다.

### 6. 규칙 조합을 사람이 모두 설계하지 않아도 된다

PBS 제약은 서로 독립적이지 않다.

```text
bay balance
P/S 연결성
작업장 순서
심수 용량
C/Seam 간격
고심수/곡판 간격
날짜별 작업 가능 시간
```

휴리스틱은 각 규칙의 우선순위를 사람이 직접 설계해야 한다.  
RL은 제약 마스킹 안에서 선택을 반복하며, 여러 제약이 동시에 작동할 때의 선택 경향을 학습할 수 있다.

## 다른 방법과의 구조적 차이

| 방법 | 강점 | 한계 | 본 문제에서의 해석 |
|---|---|---|---|
| 휴리스틱 | 빠르고 해석이 쉽다 | 규칙이 고정되어 변화 대응이 약하다 | 기준선과 현장 비교용으로 적합 |
| GA | 다양한 시퀀스를 탐색할 수 있다 | 요청이 바뀔 때마다 다시 탐색해야 한다 | 정적 비교와 보조 탐색용으로 적합 |
| MILP/CP | 수식화된 문제에 강하다 | 현장 예외와 비선형 제약이 많으면 모델이 무거워진다 | 소규모 검증 또는 부분 문제에 적합 |
| RL | 상태 변화에 따라 빠르게 다음 선택을 만든다 | 학습과 검증이 필요하다 | 동적 재스케줄링과 LLM 기반 수정 요청에 적합 |

## 발표용 문장

```text
본 문제는 고정된 입력에 대해 단일 최적해를 찾는 정적 조합 최적화 문제가 아니라,
작업 진행 상태, bay 점유 상태, 날짜별 용량, 생산 제약, 작업자 요청이 계속 변하는
순차 의사결정 문제이다.

따라서 본 연구는 제약 기반 action masking으로 현장 불가능 후보를 제거하고,
남은 후보 중 장기적인 makespan 및 제약 위반 영향을 고려하여 선택하는 RL policy를 사용한다.

또한 LLM interface를 통해 작업자의 자연어 수정 요청을 fixed position, precedence,
bay assignment, date cap 등의 구조화된 제약으로 변환하고, RL policy가 해당 제약을
반영하여 빠르게 재스케줄링한다.
```

## 테스트에 사용한 모델

### 생성 데이터 전체 벤치마크

`PPO/eval/all_methods`의 RL/휴리스틱/GA 통합 결과는 생성 데이터 격자 실험 기준이다.

대화에서 생성 데이터 평가 명령에 사용한 RL 모델은 다음이다.

```text
PPO/train/result/models/0422_14_55_ranger_adabelief_diff_envTrue/best_ppo_rollout_ep400.pth
```

주요 설정은 다음과 같았다.

```text
methods: RL,LPT,SPT,SEAM_MIN,GA
generation_mode: grid
block_counts: 20:200:10
sampling: 50
profile_sampling: 1
heuristic_profile_sampling: 1
rl_selection_mode: best_pm
```

통합 결과 위치:

```text
PPO/eval/all_methods
```

### 실적 데이터 및 LLM/UI 데모용 테스트

실적 데이터 테스트와 LLM/UI 재스케줄링 실험에서 사용하려고 지정했던 최신 쪽 모델은 다음이다.

```text
PPO/train/result/models/0428_11_36_ranger_adabelief_diff_envTrue/best_ppo_rollout_ep6600.pth
```

이 모델은 생성 데이터 전체 벤치마크의 `all_methods` 결과 모델과 구분해서 기록해야 한다.

## 주의할 표현

아래 표현은 약하다.

```text
LLM을 쓰기 때문에 RL이어야 한다.
```

대신 다음처럼 말하는 것이 정확하다.

```text
LLM은 자연어 요청을 구조화된 제약으로 바꾸고,
RL은 그 제약을 반영한 동적 상태에서 빠르게 새 스케줄을 생성한다.
```
