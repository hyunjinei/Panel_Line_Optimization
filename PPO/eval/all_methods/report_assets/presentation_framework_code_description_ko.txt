[AGENT-ADD] 발표용 코드 기반 문제 해결 프레임워크 설명

파일 목적
이 문서는 현재 코드가 Panel-Line Scheduling 문제를 어떻게 풀고 있는지 발표용 프레임워크로 설명하기 위한 정리본이다.
그림을 만들 때는 아래 흐름을 기준으로 박스를 배치하면 된다.
특히 Bay divide, 즉 공통 공정 이후 35A와 36B로 나뉘는 구조를 반드시 보여야 한다.


1. 코드가 푸는 문제

이 코드는 조선 패널 라인에서 여러 블록을 어떤 순서로 투입하고, 각 블록을 어느 베이에 배정할지 결정하는 스케줄링 문제를 푼다.

입력은 각 블록의 속성이다.
- 블록 번호와 이름
- 공정별 처리 시간
- 조립 착수 기준일
- 심수와 C/Seam 수
- 폭, 길이, 론지 수
- P/S 쌍 여부
- 라인 조립, 고정, 사내, 사외 등 작업 성격
- 곡판, 주판 Only, 고론지, 자재 준비 여부

결정해야 하는 것은 두 가지다.
- 첫째, 남은 블록 중 다음에 투입할 블록을 선택한다.
- 둘째, 선택된 블록을 35A 또는 36B 베이에 배정한다.

최종 목표는 두 가지다.
- 전체 완료 시간인 makespan을 줄인다.
- 실제 생산 제약 위반을 줄인다.

따라서 이 문제는 단순 정렬 문제가 아니라, 순서 선택, 제약 만족, Bay divide, 그리고 공정 완료 시간 계산이 함께 들어간 현실형 생산 스케줄링 문제다.


2. 전체 해결 흐름

발표 그림에서는 다음 흐름을 큰 박스로 보여주면 된다.

Input Block Data
-> Enhanced PBS Environment
-> Constraint Masking
-> Scheduler Selection
-> Bay Divide and Makespan Engine
-> Final Audit and Result Analysis

LLM Connect를 넣는 경우에는 별도 옆 박스로 둔다.

Operator Request
-> LLM Interface
-> Structured Constraints
-> Existing Scheduler
-> Final Audit
-> LLM Explanation

중요한 점은 LLM이 스케줄을 직접 만드는 것이 아니라는 점이다.
LLM은 작업자 요청을 구조화된 제약으로 바꾸고, 기존 LPT/RL 스케줄러와 최종 검증 결과를 바탕으로 설명한다.


3. 실행 진입점

main.py가 전체 실행 모드를 나눈다.

- train 모드: PPO.train.runner 실행
- eval 또는 compare 모드: PPO.eval.runner 실행
- llm 모드: llm_interface.cli 실행

코드 기준:
- main.py
- PPO/train/runner.py
- PPO/eval/runner.py
- llm_interface/cli.py

즉 발표에서는 main.py를 통합 실행기라고 설명하면 된다.


4. 환경과 상태 관리

EnhancedPanelBlockShop 환경은 스케줄링 상태를 관리한다.
환경은 블록 목록, 시작 시각, 제약 설정, 메타데이터를 받아 초기화된다.

환경 안에는 여러 매니저가 들어간다.
- CapacityTracker: 일별 심수와 블록 수 용량 관리
- PSBlockManager: P/S 쌍 순서와 짝 관계 관리
- BayStateTracker: 35A, 36B 베이 상태 관리
- CalendarManager: 주말, 공휴일, 혹서기 등 달력 조건 관리
- ConstraintChecker: 다음 후보 블록 마스킹
- ConstraintValidator: 최종 결과 검증

코드 기준:
- enhanced_environment/pbs_env/core.py
- enhanced_environment/constraints/managers/capacity_manager.py
- enhanced_environment/constraints/managers/ps_manager.py
- enhanced_environment/constraints/managers/bay_manager.py
- enhanced_environment/constraints/managers/calendar_manager.py
- enhanced_environment/masking/core.py
- enhanced_environment/bay/validator/

발표 표현:
"Environment는 단순한 시뮬레이터가 아니라, 현재 생산 상태와 실제 제약 매니저를 함께 가진 상태 기반 스케줄링 환경이다."


5. 후보 블록 마스킹

스케줄러는 모든 블록을 자유롭게 고르지 않는다.
먼저 ConstraintChecker가 현재 시점에서 선택 가능한 후보만 걸러낸다.

주요 마스킹 조건은 다음과 같다.
- 조립 착수 기준일과 작업장 창
- 일별 심수 용량
- 일별 블록 수 용량
- P/S 순서
- 라인 조립, 고정, 사내, 사외 혼합 규칙
- C/Seam 간격
- 곡판 간격
- 고심수 간격
- 연속 3 Bay 위험 패턴
- 자재 준비 여부

후보가 너무 적거나 없으면, 설정된 순서대로 일부 제약을 완화하면서 후보를 다시 찾는다.
하지만 P/S 순서처럼 절대 우회하면 안 되는 규칙은 계속 유지된다.

코드 기준:
- enhanced_environment/masking/core.py
- enhanced_environment/masking/capacity.py
- enhanced_environment/masking/ps_mixing.py
- enhanced_environment/masking/routing.py
- enhanced_environment/masking/workshop_window.py

발표 표현:
"Action masking은 RL이 불가능한 선택을 학습하지 않도록 후보 공간을 현실 제약 안으로 줄이는 단계다."


6. 스케줄러 선택

후보 블록이 정해지면 스케줄러가 그중 하나를 고른다.

기존 비교 방법:
- SPT: 처리 시간이 짧은 블록 우선
- LPT: 처리 시간이 긴 블록 우선
- SEAM_MIN 또는 MSF: 심수 부담이 작은 블록 우선
- GA: 유전 알고리즘 기반 탐색
- RL: 학습된 정책으로 후보 블록 선택

RL 경로에서는 SingleStepPtrNet이 후보 블록을 점수화한다.
이 모델은 블록 특징과 환경 상태를 입력으로 받아, 현재 후보 중 다음 블록의 확률을 계산한다.
마스킹된 후보 밖의 블록은 선택 대상이 아니다.

코드 기준:
- scheduling/assembly_start/rl_assembly_scheduler.py
- PPO/models/single_step_actor.py
- PPO/train/assembly_rollout.py

발표 표현:
"RL은 전체 블록을 무작정 고르는 것이 아니라, 제약 마스킹으로 걸러진 후보 중에서 makespan과 위반 수를 줄이는 방향의 선택 정책을 학습한다."


7. Bay divide가 중요한 이유

이 코드에서 Bay divide는 단순한 표시가 아니다.
블록을 선택한 뒤에는 반드시 35A 또는 36B 베이를 배정한다.
이 배정은 이후 makespan 계산과 제약 위반에 직접 영향을 준다.

Bay divide 구조:
- 공정 1~5는 공통 라인에서 처리된다.
- 공정 6~8은 35A 또는 36B 베이로 나뉘어 처리된다.
- 따라서 같은 투입 순서라도 35A/36B 배정이 달라지면 공정 대기 시간과 최종 makespan이 달라진다.

코드의 makespan 계산은 세 개의 완료 시간 표를 쓴다.
- ct_common: 공통 공정 1~5
- ct_branch_a: 35A 베이 공정 6~8
- ct_branch_b: 36B 베이 공정 6~8

코드 기준:
- enhanced_environment/bay/makespan/core.py

발표 그림에서는 반드시 아래 구조를 보여야 한다.

Common Process 1~5
-> Bay Divide
   -> 35A Branch Process 6~8
   -> 36B Branch Process 6~8
-> Final Completion

이 그림이 없으면 코드의 핵심인 "순서 선택 + 베이 분기 + 병렬 공정 시간 계산"이 잘 보이지 않는다.


8. Bay 배정 규칙

블록이 선택되면 env._auto_assign_bay가 베이를 배정한다.
실제 로직은 enhanced_environment/bay/assigner/core.py에 분리되어 있다.

Bay 배정 우선순위는 다음과 같다.

1. P/S small 쌍
   - 론지 수가 작은 P/S 쌍은 같은 베이로 묶는다.
   - 필요한 경우 36B를 우선 사용한다.

2. 폭 제약
   - 폭이 21m를 넘는 블록은 36B로 강제한다.

3. 연속 배치 제약
   - 같은 베이 연속 배치가 위험하면 반대 베이로 보낸다.
   - 연속 3 Bay 위험을 줄인다.

4. 특수 블록 규칙
   - 10번 블록은 36B 관련 규칙을 따른다.
   - 론지 30개 이상 블록은 35A를 우선한다.

5. 부하 균등
   - 35A와 36B의 누적 작업 시간 또는 누적 론지 수를 비교한다.
   - 부하가 적은 베이를 우선 선택한다.

BayStateTracker는 다음 상태를 계속 저장한다.
- 35A 누적 작업 시간
- 36B 누적 작업 시간
- 35A 블록 수
- 36B 블록 수
- 35A 누적 론지 수
- 36B 누적 론지 수
- 연속 베이 배정 수
- P/S 원자 단위 처리 기록

코드 기준:
- enhanced_environment/pbs_env/bay_ops.py
- enhanced_environment/bay/assigner/core.py
- enhanced_environment/constraints/managers/bay_manager.py

발표 표현:
"Bay divide는 선택된 블록을 실제 생산 라인의 두 분기 중 어디로 보낼지 결정하는 단계이며, 이후 공정 대기와 makespan을 바꾸는 핵심 결정 변수다."


9. Makespan 계산

makespan 계산기는 선택된 순서와 Bay 배정을 받아 공정별 완료 시간을 계산한다.

계산 방식:
- 각 블록은 공정 1부터 공정 8까지 순서대로 진행한다.
- 공통 공정 1~5는 하나의 공통 라인 완료 시간 표를 따른다.
- 공정 6~8은 배정된 베이의 완료 시간 표를 따른다.
- 각 공정 시작 시점은 두 조건 중 늦은 시점이다.
  - 같은 블록의 이전 공정 완료 시점
  - 같은 기계 또는 같은 베이에서 이전 블록이 끝난 시점
- 전체 makespan은 공통 공정과 두 베이 분기 공정의 최대 완료 시간이다.

코드 기준:
- enhanced_environment/bay/makespan/core.py

발표 표현:
"Makespan은 단순 처리 시간 합이 아니라, 공통 공정과 35A/36B 분기 공정의 대기 관계를 반영한 완료 시간 표로 계산된다."


10. 최종 검증과 결과 저장

블록 선택, Bay 배정, makespan 계산이 끝나면 검증 단계가 수행된다.
검증 결과는 ConstraintViolation으로 저장된다.

결과 row에는 다음 정보가 포함된다.
- 선택 순서
- block_id와 block_name
- 할당 Bay
- 공정별 처리 시간
- 시작 시간과 종료 시간
- makespan
- 제약 위반 수
- 제약 위반 종류
- P/S, line group, 폭, 론지, 심수 등 블록 속성

코드 기준:
- scheduling/common/result_builders.py
- enhanced_environment/common/violation_utils.py
- enhanced_environment/bay/validator/

발표 표현:
"최종 평가는 makespan 하나만 보는 것이 아니라, audit 단계에서 제약 위반을 다시 세고 결과 row에 함께 저장한다."


11. LLM Connect의 역할

LLM Connect는 스케줄러를 대체하지 않는다.
역할은 세 가지다.

첫째, 작업자 자연어 요청을 구조화된 제약으로 바꾼다.
예:
- "1번 블록을 먼저 넣어줘"
- "12번은 35A로 보내줘"
- "C/Seam은 runtime만 완화하고 audit는 유지해줘"

둘째, 구조화된 제약을 기존 스케줄러에 전달한다.
가능한 구조화 제약은 다음과 같다.
- fixed_position
- precedence
- manual_bay_assignment
- date_specific_daily_block_cap
- date_specific_daily_seam_cap
- constraint_toggle
- bias_components

셋째, 재스케줄 전후 결과와 최종 검증 결과를 바탕으로 설명을 만든다.
설명은 makespan 변화, 제약 위반 변화, Bay 배정 변화, 순서 변화에 근거한다.

코드 기준:
- llm_interface/parser.py
- llm_interface/openai_parser.py
- llm_interface/reschedule.py
- llm_interface/analysis_bundle.py
- llm_interface/result_explainer.py
- experiments/interactive_llm_reschedule.py
- apps/streamlit_scheduler_chat.py

발표 표현:
"LLM은 request-to-constraint interface와 audit-grounded explanation 계층이다. 실제 재스케줄링 계산은 기존 LPT/RL 스케줄러가 수행한다."


12. 발표용 프레임워크 그림 제안

그림은 복잡한 글보다 구조가 먼저 보여야 한다.
추천 그림 구조는 다음과 같다.

왼쪽:
Input Block Data
- block attributes
- process times
- P/S pair
- seam and longi
- assembly date

중앙 왼쪽:
Enhanced PBS Environment
- capacity manager
- P/S manager
- calendar manager
- bay state tracker
- constraint checker

중앙:
Constraint Masking
- feasible candidate set
- hard rule filter
- staged relaxation

중앙 오른쪽:
Scheduler
- LPT / SPT / SEAM_MIN / GA
- RL policy
- selected next block

오른쪽 핵심:
Bay Divide and Makespan Engine
- Common process 1~5
- 35A branch process 6~8
- 36B branch process 6~8
- CT tables
- makespan

맨 오른쪽:
Final Audit and Analysis
- violations
- makespan
- sequence diff
- bay diff
- result csv

LLM Connect는 위쪽 또는 아래쪽에 side-car 형태로 둔다.

Operator Request
-> LLM Interface
-> Structured Constraints
-> Existing Scheduler
-> Final Audit
-> LLM Explanation

주의:
- LLM 박스를 스케줄러보다 크게 그리지 않는다.
- LLM이 next block을 직접 고르는 것처럼 그리지 않는다.
- Bay divide는 반드시 공통 공정 뒤에서 35A/36B로 갈라지는 형태로 그린다.
- Final Audit은 단순 makespan만이 아니라 제약 위반과 Bay 변화까지 포함한다.


13. 한 문장 요약

이 코드는 패널 블록의 투입 순서를 선택하고, 선택된 블록을 35A/36B Bay로 나누어 배정한 뒤, 공통 공정과 Bay 분기 공정의 완료 시간 표를 계산하여 makespan과 제약 위반을 함께 최소화하는 현실형 Panel-Line Scheduling 프레임워크이다.

LLM은 이 프레임워크 위에서 작업자 요청을 구조화된 제약으로 바꾸고, 기존 스케줄러가 만든 결과를 최종 검증 결과에 근거해 설명하는 보조 계층으로 동작한다.
